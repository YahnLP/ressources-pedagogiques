### Points de Vigilance

⚠️ **Bind9 – Syntaxe des fichiers de zone : tolérance zéro**
Les fichiers de zone DNS ont une syntaxe très stricte :
- Le **point final** après chaque FQDN (Fully Qualified Domain Name) est **OBLIGATOIRE** : `ns1.techpro.local.` ≠ `ns1.techpro.local`
- Le **numéro de série SOA** doit être incrémenté après chaque modification (convention : YYYYMMDDNN)
- Les **tabulations vs espaces** : Bind9 est permissif mais la cohérence est importante
- Commande de vérification : `sudo named-checkzone` et `sudo named-checkconf` → **toujours lancer avant reload**

⚠️ **Bind9 – Fichier named.conf.local vs named.conf.options**
- `named.conf.options` : paramètres globaux (forwarders, recursion, allow-query)
- `named.conf.local` : déclaration des zones locales (zone "techpro.local")
- **Ne pas confondre les deux fichiers** : erreur très fréquente en TP

⚠️ **Bind9 – Permissions des fichiers de zone**
- Les fichiers de zone doivent appartenir à `bind:bind` : `sudo chown bind:bind /etc/bind/db.techpro.local`
- Sans ça, `named` ne peut pas lire le fichier → zone non chargée

⚠️ **STP – Précision sur le root bridge**
- Le root bridge n'est PAS forcément le switch le plus puissant — c'est celui avec la **priorité la plus basse** (défaut 32768)
- En cas d'égalité de priorité : **MAC la plus basse** (numérique)
- En production, on force le root bridge avec `spanning-tree vlan 1 priority 4096` sur le switch central
- **Danger pédagogique** : les étudiants pensent souvent que "priorité haute = root bridge" → rappeler que c'est l'inverse (priorité 0 = gagnant absolu)

⚠️ **STP dans Packet Tracer – Délai de convergence**
- Le STP classique (802.1d) prend **30 à 50 secondes** pour converger après un changement
- Les voyants passent par : Orange (Listening/Learning) → Vert (Forwarding) → certains Orange puis Orange fixe (Blocking)
- Prévenir les étudiants d'**attendre la convergence** avant de tester la connectivité

### Ressources Complémentaires pour l'Enseignant

**Commandes de diagnostic DNS :**
```bash
# dig : outil de référence pour interroger un serveur DNS
dig @127.0.0.1 www.techpro.local A        # Requête A (nom → IP)
dig @127.0.0.1 -x 192.168.10.10           # Requête PTR (IP → nom) / zone inverse
dig @127.0.0.1 techpro.local NS           # Serveurs de noms
dig @127.0.0.1 techpro.local SOA          # Enregistrement SOA
dig @8.8.8.8 www.google.fr               # Interroger un serveur externe

# nslookup : plus simple, disponible Windows et Linux
nslookup www.techpro.local 127.0.0.1     # Requête directe
nslookup 192.168.10.10 127.0.0.1         # Requête inverse

# host : résolution simple
host www.techpro.local 127.0.0.1
host 192.168.10.10 127.0.0.1

# Vérification de la config Bind9
sudo named-checkconf                      # Vérifier named.conf
sudo named-checkzone techpro.local /etc/bind/db.techpro.local
sudo named-checkzone 10.168.192.in-addr.arpa /etc/bind/db.192.168.10.rev
```

**Structure des fichiers Bind9 :**
```
/etc/bind/
├── named.conf                    # Fichier principal (inclut les suivants)
├── named.conf.options            # Options globales (forwarders, recursion)
├── named.conf.local              # Zones locales (à modifier)
├── named.conf.default-zones      # Zones par défaut (localhost, root hints)
├── db.techpro.local              # Zone directe (à créer)
└── db.192.168.10.rev             # Zone inverse (à créer)
```

**Commandes Cisco STP :**
```cisco
! Afficher le STP
Switch# show spanning-tree                        ! Vue globale STP VLAN 1
Switch# show spanning-tree vlan 1                 ! STP pour VLAN 1 spécifique
Switch# show spanning-tree detail                 ! Détail complet (coûts, timers)
Switch# show spanning-tree interface Fa0/1        ! STP sur une interface
Switch# show spanning-tree summary                ! Résumé : root bridge, ports

! Modifier la priorité (forcer le root bridge)
Switch(config)# spanning-tree vlan 1 priority 4096    ! Multiples de 4096
Switch(config)# spanning-tree vlan 1 root primary     ! Macro : met 24576
Switch(config)# spanning-tree vlan 1 root secondary   ! Macro : met 28672

! Modes STP
spanning-tree mode pvst           ! Per-VLAN STP (classique 802.1d) - défaut
spanning-tree mode rapid-pvst     ! Rapid PVST+ (802.1w) - convergence rapide
```

>
> *DNS = Domain Name System = le grand annuaire d'Internet et des réseaux locaux.*

### Déroulé (25 minutes)

#### Phase 1 : Distribution des Rôles (3 min)

Groupes de **5** :

| **Joueur** | **Rôle** | **Ce qu'il sait** |
|------------|----------|-------------------|
| Apprenant 1 | **Le Client (navigateur)** | Veut savoir l'IP de `www.techpro.local` |
| Apprenant 2 | **Résolveur (resolver DNS du PC / box)** | Ne sait pas encore – va chercher pour le client |
| Apprenant 3 | **Serveur DNS Racine (Root Server)** | Sait qui gère `.local` → renvoie vers le serveur autoritaire local |
| Apprenant 4 | **Serveur DNS Autoritaire** (techpro.local) | Possède le fichier de zone → sait que `www` = `192.168.10.50` |
| Apprenant 5 | **Le Cache** (observateur/notaire) | Note les réponses sur une feuille "cache" pour les prochaines fois |

Chaque joueur reçoit une **carte de rôle** avec ses informations.

---

#### Phase 2 : Simulation – Tour 1, Cache Vide (12 min)

**Étape 1 : Le client interroge le Résolveur**

Le **Client** (navigateur) tend un billet au **Résolveur** :
```
QUESTION DNS : Quelle est l'adresse IP de www.techpro.local ?
```

**Étape 2 : Le Résolveur vérifie son cache**

Le **Résolveur** consulte le **Cache** (feuille vierge) :
> *"Rien dans le cache. Je dois chercher."*

**Étape 3 : Le Résolveur interroge le serveur Racine**

Le **Résolveur** demande au **Serveur Racine** :
> *"Qui gère le domaine `.local` ?"*

Le **Serveur Racine** répond :
> *"Je ne connais pas `www.techpro.local` directement, mais voici qui gère `.local` : c'est le Serveur Autoritaire de techpro.local à l'adresse 192.168.10.1"*

**Étape 4 : Le Résolveur interroge le Serveur Autoritaire**

Le **Résolveur** demande au **Serveur Autoritaire** :
> *"Quelle est l'IP de `www.techpro.local` ?"*

Le **Serveur Autoritaire** consulte son fichier de zone (sa fiche) et répond :
> *"`www.techpro.local` → `192.168.10.50` (type A, TTL 3600)"*

**Étape 5 : Le Résolveur stocke et répond au Client**

Le **Résolveur** remet la réponse au **Client** :
> *"`www.techpro.local` = `192.168.10.50`"*

Le **Cache** note : `www.techpro.local → 192.168.10.50 (expire dans 3600 secondes)`

---

#### Phase 3 : Tour 2, Avec Cache (4 min)

**Même requête** : le Client redemande l'IP de `www.techpro.local`.

Le **Résolveur** consulte le **Cache** :
> *"Trouvé ! Pas besoin d'interroger les serveurs — la réponse est encore valide."*

Le **Résolveur** répond immédiatement au **Client** depuis le cache.

→ **Conclusion :** Le TTL (Time To Live) évite les requêtes répétées inutiles. C'est pourquoi les changements DNS ne sont pas instantanés — il faut attendre l'expiration du TTL du cache.

---

#### Phase 4 : Débriefing (6 min)

**Questions :**

1. *"Combien d'échanges réseau ont eu lieu lors de la première résolution ? Et lors de la seconde ?"*
   - Tour 1 : 4 échanges (Client→Résolveur, Résolveur→Racine, Résolveur→Autoritaire, Résolveur→Client)
   - Tour 2 : 1 échange (Résolveur répond directement depuis cache)

2. *"Si on change l'IP d'un serveur web dans le DNS, pourquoi les utilisateurs voient-ils parfois encore l'ancienne IP pendant quelques heures ?"*
   - Réponse : TTL — le cache a encore l'ancienne réponse valide. Il faut attendre expiration.

3. *"Que se passe-t-il si le Serveur Autoritaire est en panne ?"*
   - Réponse : Les nouvelles résolutions échouent. Les résolutions en cache continuent de fonctionner (jusqu'à expiration du TTL).

4. *"Dans notre réseau local, a-t-on besoin du Serveur Racine d'Internet pour résoudre `www.techpro.local` ?"*
   - Réponse : Non ! Le serveur DNS local est autoritaire pour `techpro.local` — il répond directement. Le serveur racine sert pour les domaines publics (google.fr, etc.).

**Transition :**

> *"Parfait — vous venez de simuler la résolution DNS récursive ! Passons maintenant à la configuration du serveur DNS Bind9 sous Linux, qui jouera le rôle de Serveur Autoritaire dans notre réseau."*

### I. Le Service DNS

#### A. Pourquoi le DNS ?

Les machines communiquent par **adresses IP** (192.168.10.50). Les humains retiennent des **noms** (www.techpro.local, google.fr).

**Le DNS** (Domain Name System) fait le lien : il traduit les noms de domaine en adresses IP, et inversement.

**Sans DNS :** Vous devriez mémoriser l'IP de chaque site web. `http://142.250.185.78` à la place de `http://www.google.fr`.

**Avec DNS :** Vous tapez un nom, le système trouve l'IP pour vous, de façon transparente.

---

#### B. Vocabulaire Essentiel

| **Terme** | **Définition** | **Exemple** |
|-----------|----------------|-------------|
| **Domaine** | Espace de noms hiérarchique | `techpro.local`, `google.fr` |
| **FQDN** | Fully Qualified Domain Name – nom complet avec le point final | `www.techpro.local.` |
| **Zone** | Portion de l'espace de noms gérée par un serveur DNS | Zone `techpro.local` gérée par `ns1.techpro.local` |
| **Zone directe** | Traduit noms → adresses IP | `www` → `192.168.10.50` |
| **Zone inverse** | Traduit adresses IP → noms | `192.168.10.50` → `www.techpro.local.` |
| **Résolveur** | Client DNS qui interroge les serveurs | Pile réseau du PC, box Internet |
| **Serveur autoritaire** | Possède les fichiers de zone et fait référence | Le serveur Bind9 qu'on configure |
| **Cache DNS** | Mémorisation temporaire des réponses (durée = TTL) | Cache de la box, du PC |
| **TTL** | Time To Live – durée de validité d'un enregistrement en cache | `3600` = 1 heure |
| **Forwarder** | Serveur DNS vers lequel on renvoie les requêtes non résolues localement | `8.8.8.8` (Google DNS) |

---

#### C. Les Types d'Enregistrements DNS

Chaque ligne dans un fichier de zone est un **enregistrement DNS (Resource Record)**.

| **Type** | **Nom** | **Rôle** | **Exemple** |
|----------|---------|----------|-------------|
| **A** | Address | Nom → IPv4 | `www IN A 192.168.10.50` |
| **AAAA** | Address IPv6 | Nom → IPv6 | `www IN AAAA 2001:db8::1` |
| **PTR** | Pointer | IPv4 → Nom (zone inverse) | `50 IN PTR www.techpro.local.` |
| **CNAME** | Canonical Name | Alias pointant vers un autre nom | `web IN CNAME www` |
| **NS** | Name Server | Serveur de noms autoritaire pour la zone | `@ IN NS ns1.techpro.local.` |
| **MX** | Mail Exchanger | Serveur de messagerie | `@ IN MX 10 mail.techpro.local.` |
| **SOA** | Start of Authority | Informations d'autorité de la zone | (voir ci-dessous) |
| **TXT** | Text | Enregistrement texte libre (SPF, DKIM...) | `@ IN TXT "v=spf1 mx -all"` |

---

#### D. Le Processus de Résolution DNS

Il existe deux types de résolution :

##### 🔹 Résolution Récursive (vue du client)

Le client pose **une seule question** au résolveur et attend **une seule réponse complète**. Le résolveur fait tout le travail.

```
Client          Résolveur            Serveur Racine     Serveur Autoritaire
  │                  │                      │                    │
  │──"www.google.fr?"│                      │                    │
  │                  │──"Qui gère .fr ?" ──>│                    │
  │                  │<─"ns1.nic.fr"────────│                    │
  │                  │─────"Qui gère google.fr ?" ─────────────>│
  │                  │<────"ns1.google.com" ───────────────────│
  │                  │─────"IP de www.google.fr ?" ───────────>│
  │                  │<────"142.250.185.78" ────────────────────│
  │<─"142.250.185.78"│                      │                    │
```

##### 🔹 Résolution Itérative (vue du résolveur)

Le serveur renvoie la **meilleure réponse** qu'il peut donner (pas une réponse complète). Le résolveur pose ensuite la question au serveur suivant. C'est la mécanique interne que le résolveur utilise.

---

#### E. Zones Directe et Inverse

##### 🔹 Zone Directe (forward zone)

Traduit des **noms → adresses IP** via des enregistrements **A**.

**Fichier de zone directe `db.techpro.local` (exemple) :**
```
$TTL 3600                        ; TTL par défaut : 1 heure
@ IN SOA ns1.techpro.local. admin.techpro.local. (
                2024112001       ; Serial : YYYYMMDDNN
                3600             ; Refresh : 1h
                900              ; Retry : 15min
                604800           ; Expire : 1 semaine
                3600 )           ; Negative cache TTL : 1h

; Serveur(s) de noms
@ IN NS ns1.techpro.local.

; Enregistrements A (nom → IP)
ns1      IN A 192.168.10.1       ; Serveur DNS lui-même
www      IN A 192.168.10.50      ; Serveur web
mail     IN A 192.168.10.51      ; Serveur mail
srv-nas  IN A 192.168.10.10      ; NAS

; Alias CNAME
web      IN CNAME www            ; "web" pointe vers "www"
intranet IN CNAME www
```

**Lecture :**
- `@` = origine de la zone (= `techpro.local.`)
- `IN` = classe Internet (toujours IN)
- Un nom sans point final est **relatif** à la zone (`www` = `www.techpro.local.`)
- Un nom **avec point final** est **absolu** (FQDN) : `ns1.techpro.local.`

---

##### 🔹 Zone Inverse (reverse zone)

Traduit des **adresses IP → noms** via des enregistrements **PTR**.

Le nom de la zone inverse pour `192.168.10.0/24` est : `10.168.192.in-addr.arpa`
*(les octets du réseau sont inversés, + `.in-addr.arpa`)*

**Fichier de zone inverse `db.192.168.10.rev` (exemple) :**
```
$TTL 3600
@ IN SOA ns1.techpro.local. admin.techpro.local. (
                2024112001
                3600
                900
                604800
                3600 )

@ IN NS ns1.techpro.local.

; Enregistrements PTR (dernier octet de l'IP → nom complet)
1  IN PTR ns1.techpro.local.
10 IN PTR srv-nas.techpro.local.
50 IN PTR www.techpro.local.
51 IN PTR mail.techpro.local.
```

**Lecture :**
- `1 IN PTR ns1.techpro.local.` → l'IP `192.168.10.1` (zone `10.168.192.in-addr.arpa`) correspond à `ns1.techpro.local.`
- On n'écrit que le **dernier octet** (le reste est dans le nom de la zone)
- Le nom cible d'un PTR doit **toujours** avoir un point final

---

#### F. L'Enregistrement SOA – Start of Authority

L'enregistrement SOA est le premier de chaque zone. Il contient les métadonnées de la zone.

```
@ IN SOA ns1.techpro.local. admin.techpro.local. (
          2024112001   ; Serial
          3600         ; Refresh
          900          ; Retry
          604800       ; Expire
          3600 )       ; Negative TTL
```

| **Champ** | **Rôle** |
|-----------|----------|
| `ns1.techpro.local.` | Serveur DNS primaire de la zone |
| `admin.techpro.local.` | Email de l'administrateur (le `.` remplace le `@`) |
| **Serial** | Numéro de version (convention : AAAAMMJJNN). Doit être incrémenté à chaque modif pour que les secondaires rechargent la zone |
| **Refresh** | Délai entre deux vérifications du secondaire (en secondes) |
| **Retry** | Délai avant nouvelle tentative si le secondaire ne peut pas contacter le primaire |
| **Expire** | Durée après laquelle le secondaire considère sa copie comme obsolète |
| **Negative TTL** | Durée de mise en cache d'une réponse NXDOMAIN (nom inexistant) |

### II. Spanning Tree Protocol (STP)

#### A. Le Problème des Boucles Réseau

En commuté (switches), on peut être tenté de relier plusieurs switches par plusieurs câbles pour la **redondance** (si un lien tombe, l'autre prend le relais). Mais cela crée des **boucles physiques**.

**Problème 1 : Tempête de broadcast (Broadcast Storm)**

```
[SW1]────────────────[SW2]
  │                    │
  └──────[SW3]─────────┘

PC-A envoie un broadcast :
1. SW1 reçoit → Flood vers SW2 et SW3
2. SW2 reçoit de SW1 → Flood vers SW3 (et SW1 !)
3. SW3 reçoit de SW1 et SW2 → Flood vers SW1 et SW2...
→ Tempête ! Le broadcast tourne indéfiniment, saturant le réseau à 100%
```

**Problème 2 : Instabilité de la table MAC**

Un switch reçoit la même trame de plusieurs ports → la MAC Source change de port → la table MAC est mise à jour en boucle → tous les paquets sont floodés.

**Conséquence :** Sans protection, une boucle réseau rend le réseau totalement inutilisable en quelques secondes.

---

#### B. La Solution : STP (802.1d)

**STP** (Spanning Tree Protocol) est un protocole de couche 2 qui :
1. **Détecte** automatiquement les boucles
2. **Bloque** logiquement certains ports pour casser la boucle
3. **Réactive** les ports bloqués si un lien principal tombe (redondance)

**Principe :** STP construit un **arbre recouvrant** (spanning tree) — une topologie sans boucle — en désactivant logiquement les liens redondants.

```
Avant STP (boucle) :           Après STP (arbre sans boucle) :
[SW1]───[SW2]                  [SW1]───[SW2]
  │       │             →        │
  └──[SW3]┘                    [SW3]
                         (lien SW3-SW2 bloqué logiquement)
```

---

#### C. Fonctionnement de STP : Les 4 Étapes

##### Étape 1 : Élection du Root Bridge (Pont Racine)

Tous les switches échangent des messages **BPDU** (Bridge Protocol Data Unit) contenant leur **Bridge ID**.

**Bridge ID = Priorité (16 bits) + Adresse MAC (48 bits)**

- **Priorité par défaut :** 32768 (sur tous les switches Cisco 2960)
- **Le switch avec le Bridge ID le plus petit devient Root Bridge**
- En cas d'égalité de priorité → le switch avec la **MAC la plus faible** gagne

**Exemple :**

| **Switch** | **Priorité** | **MAC** | **Bridge ID** | **Résultat** |
|------------|-------------|---------|---------------|--------------|
| SW1 | 32768 | 00:0A:00:00:00:01 | 32768 + 00:0A... | |
| SW2 | 32768 | 00:0A:00:00:00:02 | 32768 + 00:0A... | |
| SW3 | **4096** | 00:0A:00:00:00:03 | 4096 + 00:0A... | ✅ **ROOT BRIDGE** (priorité plus basse) |

⚠️ **Mémo :** "Priorité la **plus basse** = Root Bridge" (comme à une enchère : on veut la mise la plus basse)

##### Étape 2 : Élection des Root Ports

Sur chaque switch **non-root**, on élit le port offrant le **chemin le moins coûteux** vers le Root Bridge : le **Root Port (RP)**.

**Coût de port STP (selon la vitesse du lien) :**

| **Vitesse** | **Coût STP** |
|-------------|-------------|
| 10 Mb/s | 100 |
| 100 Mb/s (Fast Ethernet) | 19 |
| 1 Gb/s | 4 |
| 10 Gb/s | 2 |

*Principe : plus le lien est rapide, plus le coût est faible = chemin préféré*

##### Étape 3 : Élection des Designated Ports

Sur chaque **segment réseau** (chaque lien entre deux switches), un seul port est élu **Designated Port (DP)** : le port qui transmet les trames sur ce segment. C'est toujours le port du côté ayant le meilleur chemin vers le Root Bridge.

##### Étape 4 : Blocage des Ports Restants

Tout port qui n'est ni Root Port ni Designated Port devient **Alternate Port** et est placé en état **Blocking** : il ne transmet plus de trames normales, mais surveille les BPDU pour réagir en cas de panne.

---

#### D. États des Ports STP

| **État** | **Durée** | **Reçoit BPDU ?** | **Envoie BPDU ?** | **Transmet trames ?** | **Apprend MAC ?** |
|----------|-----------|-------------------|-------------------|----------------------|-------------------|
| **Blocking** | Permanent (ports redondants) | ✅ | ❌ | ❌ | ❌ |
| **Listening** | 15 secondes (Forward Delay) | ✅ | ✅ | ❌ | ❌ |
| **Learning** | 15 secondes (Forward Delay) | ✅ | ✅ | ❌ | ✅ |
| **Forwarding** | Permanent (ports actifs) | ✅ | ✅ | ✅ | ✅ |
| **Disabled** | Si admin ou erreur | ❌ | ❌ | ❌ | ❌ |

**Temps de convergence STP classique (802.1d) :**
- Détection de panne : ~20 secondes (Max Age timer)
- Listening + Learning : 2 × 15 secondes = 30 secondes
- **Total : ~50 secondes** avant qu'un lien de secours soit actif

**Remarque :** Rapid STP (802.1w / Rapid PVST+) réduit ce délai à **quelques secondes** — à voir en Année 2.

---

```cisco

! Exemple de sortie commentée :
VLAN0001
  Spanning tree enabled protocol ieee
  Root ID    Priority    32769                  ← Priorité + ID VLAN
             Address     0001.4300.0001         ← MAC du Root Bridge
             This bridge is the root            ← Ce switch EST le root bridge
             Hello Time   2 sec  Max Age 20 sec  Forward Delay 15 sec

  Bridge ID  Priority    32769  (priority 32768 sys-id-ext 1)
             Address     0001.4300.0001
             ...

Interface        Role  Sts  Cost   Prio.Nbr Type
```

**Lecture des colonnes :**
- **Role :** Root (RP), Desg (Designated), Altn (Alternate/Blocked)
- **Sts :** FWD (Forwarding), BLK (Blocking), LIS (Listening), LRN (Learning)
- **Cost :** Coût cumulatif vers le Root Bridge
- **Prio.Nbr :** Priorité du port (valeur par défaut 128)

### IV. TP Cisco – Observer le STP sur 3 Switches

#### Topologie

```
        [SW1]
       /     \
  Fa0/1       Fa0/2
     /           \
[SW2]─────────[SW3]
    Fa0/1   Fa0/1
```

Trois switches reliés en **triangle** = 3 liens, donc **1 boucle** → STP doit bloquer 1 port.

---

#### Étape 1 : Créer la Topologie dans Packet Tracer (5 min)

1. Placer **3 switches Cisco 2960** (SW1, SW2, SW3)
2. Câbler :
   - SW1 Fa0/1 ↔ SW2 Fa0/1 (câble droit)
   - SW1 Fa0/2 ↔ SW3 Fa0/1 (câble droit)
   - SW2 Fa0/2 ↔ SW3 Fa0/2 (câble droit)
3. Attendre la convergence STP (~30-50 secondes)
4. Observer les voyants : certains doivent être **orange** (Blocking) d'autres **vert** (Forwarding)

```
a) www IN A 192.168.25.50
   Type : A

   Signification : L'adresse 192.168.25.50 (dernier octet = 50) correspond au nom www.edutech.local.
   → Cet enregistrement est dans la zone inverse 25.168.192.in-addr.arpa

d) @ IN NS ns1.edutech.local.
   Type : NS (Name Server)
   Signification : Le serveur de noms autoritaire pour la zone "edutech.local" (@) est ns1.edutech.local.
```

### Partie 3.1 – Rapport STP (éléments attendus)

**Identification du problème :** Le technicien a créé une boucle physique en câblant les trois switches en triangle. Sans protection, une trame (notamment un broadcast comme une requête ARP ou DHCP) tourne indéfiniment entre les switches, chaque switch la retransmettant sur tous ses ports. La bande passante est saturée à 100 % en quelques secondes.

**Ce qu'est STP :** Le Spanning Tree Protocol (IEEE 802.1d) est un protocole de couche 2 qui détecte les boucles réseau et les élimine logiquement en bloquant certains ports. Les switches échangent des messages BPDU, élisent un switch central (Root Bridge), et désactivent logiquement les ports redondants tout en les conservant actifs physiquement pour la redondance.

**Résolution :** Après activation de STP (actif par défaut sur les switches Cisco 2960), le technicien devrait observer : un port d'un switch passe en état orange/Blocking dans Packet Tracer, les topologies actives se stabilisent, le réseau retrouve des performances normales. En cas de panne d'un lien actif, le port bloqué passera automatiquement en Forwarding après ~30-50 secondes.

### Partie 3.3 – Commandes pour forcer SW-EDU3 comme Root

```cisco
SW-EDU3# configure terminal
SW-EDU3(config)# spanning-tree vlan 1 priority 4096
SW-EDU3(config)# end
SW-EDU3# show spanning-tree

! Vérifier :
! - "This bridge is the root" apparaît sur SW-EDU3
! - Les anciens Root Ports changent sur SW-EDU1 et SW-EDU2
! - Reconvergence ~30 secondes
```

**Pourquoi multiple de 4096 ?** La valeur de priorité STP est codée sur 16 bits, mais les 4 bits de poids faible sont réservés pour l'identifiant de VLAN (Extended System ID). La priorité réelle doit donc être un multiple de 2^4 = 16, mais en pratique Cisco utilise des multiples de 4096 (= 2^12) pour des raisons de lisibilité et de convention inter-constructeurs.
